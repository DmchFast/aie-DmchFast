  Модель сохраняется в artifacts/best_model.pth. Итоговая тестовая точность указана в report.md (примерно 0.92–0.94 в эксперименте с fine-tuning).`

## 2. Постановка задачи и контекст

1. **Предметная область и задача:**
   - Задача: автоматическая классификация изображений сцен на 6 классов (город/природа и т.п.).
   - Практическая цель: показать воспроизводимый ML-пайплайн — от подготовки данных до развернутого API для инференса.
   - Целевая аудитория: преподаватель, ассессор или коллеги, проверяющие корректность эксперимента и качество сервиса.

2. **Формулировка в терминах ML:**
   - Вход: RGB-изображение произвольного размера.
   - Выход: метка класса среди `buildings`, `forest`, `glacier`, `mountain`, `sea`, `street` и распределение вероятностей по классам.
   - Ограничения: изображения размечены корректно, размер выборки средний (тысячи изображений), нет сильной class imbalance.

3. **Метрики качества:**
   - Основная: accuracy на валидации/тесте.
   - Дополнительно: precision/recall/F1 (по классам), матрица ошибок (confusion matrix) и среднее время инференса на CPU.

---

## 3. Данные

1. **Источник данных:**
   - Intel Image Classification (Kaggle): https://www.kaggle.com/puneet6060/intel-image-classification.

2. **Структура данных:**
   - `seg_train/seg_train/<class>/*.jpg` — обучающие изображения;
   - `seg_test/seg_test/<class>/*.jpg` — тестовые изображения;
   - 6 классов сцен.

3. **Предобработка и EDA:**
   - разделение `seg_train` на `data/processed/train` и `data/processed/val` (см. `notebooks/01_eda.ipynb`);
   - визуальный анализ классов и распределений;
   - для baseline используются HOG-признаки.

---

## 4. Модели и подходы

1. **Baseline:**
   - логистическая регрессия на HOG-признаках (`notebooks/02_baseline_ml.ipynb`);
   - метрики выводятся в `classification_report` и `Validation accuracy`.

2. **Transfer learning:**
   - ResNet-18 с заморозкой весов и последующим fine-tune (`notebooks/03_transfer_learning.ipynb`);
   - применяются аугментации и нормализация ImageNet.

3. **Нейросетевые особенности:**
   - батч 32, обучение в 2 этапа (frozen + fine-tune);
   - оптимизатор Adam, LR 1e-3 и 1e-4.

---

## 5. Экспериментальный протокол и результаты

1. **Протокол:**
   - train/val разбиение формируется из `seg_train`;
   - метрики считаются на валидации, логируются в MLflow.

2. **Сравнение моделей:**

   | Модель / конфигурация        | Описание                                   | Метрика (val acc) | Комментарий |
   |------------------------------|--------------------------------------------|-------------------|-------------|
   | Baseline (HOG + LogReg)      | HOG-признаки + LogisticRegression          | 0.6551601423487544 | Быстрый baseline |
   | ResNet-18 (frozen)           | Замороженные слои, линейная голова         | 0.9053             | Лучший frozen-результат |
   | ResNet-18 (fine-tune)        | Полное дообучение                          | 0.9363             | Финальная модель |

3. **Выбор финальной модели:**
   - Финальная модель: ResNet-18 после fine-tune.
   - Причины выбора: хороший баланс между качеством и скоростью инференса, невысокие требования по памяти и простота воспроизведения эксперимента.

---

## 6. Архитектура решения и сервис

1. **Пайплайн и артефакты:**
   - Подготовка: `seg_train` → `data/processed/train` + `data/processed/val` (стратифицированное разбиение).
   - Тренировка: сохранение контрольных чекпоинтов и лучшей модели в `artifacts/best_model.pth`.
   - Экспериментальная телеметрия: MLflow хранит параметры, метрики и артефакты (plots, confusion matrix).

2. **API (FastAPI):**
   - `GET /health` — возвращает статус сервиса: `{"status": "ok"}` и информацию о загрузке модели.
   - `POST /predict` — multipart/form-data, поле `file`; возвращает JSON:

```json
{
  "class": "forest",
  "probabilities": {"buildings":0.01, "forest":0.92, ...}
}
```

   - Ограничения: входные файлы проверяются по типу и размеру (например, до 5 MB).

3. **Инфраструктура:**
   - Сервис запускается локально через `uvicorn` или в контейнере Docker; конфигурации указаны в `docker/docker-compose.yml`.

## 7. Наблюдаемость, конфигурация и безопасность

1. **Логирование и мониторинг:**
   - Логи запросов и ошибок пишутся в stdout/stderr (удобно для контейнера); MLflow хранит ключевые метрики.
   - Для будущего: добавить Prometheus-exporter и визуализацию в Grafana.

2. **Конфигурация:**
   - Параметры (пути к моделям, порты, уровни логирования) — через `.env` и `configs/.env.example`.

3. **Безопасность:**
   - Секреты не хранятся в репозитории; реализована базовая проверка входных файлов.

## 8. Ограничения и дальнейшая работа

- Текущие ограничения: валидация проводилась на отложенной части `seg_train`, полный `seg_test` не использовался для финальной валидации.
- Модель обучалась без полного перебора гиперпараметров; пространство экспериментов ограничено доступным временем.

Дальнейшие шаги (приоритетные и выполнимые):

- Подтвердить результаты на полном `seg_test` и добавить отчёт по ошибкам (confusion matrix).
- Простейший гиперпараметрический поиск (Grid/Random) для LR и scheduler на ограниченном наборе конфигураций.
- Улучшить API: базовая валидация изображений, ограничение размера и обработка ошибок.

## 9. Сценарий демонстрации на защите

1. Открыть структуру проекта и кратко пройтись по ключевым файлам: `configs/`, `data/`, `notebooks/`, `src/`, `tests/`, `artifacts/`.
2. Показать подготовку данных: открыть `notebooks/01_eda.ipynb`, показать примеры изображений и распределение по классам.
3. Запустить сервис локально и выполнить запросы:

```bash
cd project
.venv\Scripts\activate
uvicorn src.app:app --host 127.0.0.1 --port 8000
# В другом терминале
curl http://127.0.0.1:8000/health
curl -X POST "http://127.0.0.1:8000/predict" -F "file=@C:\path\to\image.jpg"
```

4. Показать `notebooks/03_transfer_learning.ipynb`: сравнение метрик, сохранить `artifacts/best_model.pth` и объяснить выбор финальной модели.
5. Коротко продемонстрировать тесты: `pytest -q tests`.

См. подробные команды и примеры в `project/README.md`.


### через Docker (альтернативный способ)

Для демонстрации можно запустить сервис в контейнере через `docker-compose`:

```bash
cd project

# Собрать и запустить сервис в контейнерах
docker compose -f docker/docker-compose.yml up --build

# В другом терминале можно проверить сервис
curl http://127.0.0.1:8000/health
curl -X POST "http://127.0.0.1:8000/predict" -F "file=@C:\path\to\image.jpg"
```

При использовании Docker контейнер отдаёт сервис на порту, указанном в `docker-compose.yml` (по умолчанию `8000`).
